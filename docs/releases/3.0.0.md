# Release 3.0.0

## Breaking changes

Menagerie 3 requires a fresh state directory. It does not migrate 2.x registries.
Before upgrading, stop Menagerie and preserve the old application and state for
rollback. Keep downloaded models and runtime installations intact; they can be
registered again by path. Do not delete them to reset configuration. Restore the
old application and its matching state together if rolling back.

## Engine-led deployments

- New configurations omit tuning flags. Supported engines can select context,
  concurrency and offload automatically. Explicit values remain explicit.
- The default placement leaves engine devices visible. Select one GPU to restrict
  CUDA visibility, or use advertised native device/split/tensor options for more
  granular placement. Automatic allocation does not guarantee good performance.
- Compatible forks use the same adapter as upstream builds. Installation source,
  version and probed capabilities remain specific to each installed executable.
  There is no separate Prism adapter or filename-based compatibility rule.
- Supported standalone on-demand deployments use native idle sleep. Menagerie
  retains process supervision; coordinated groups retain atomic supervisor control.
- Multi-model deployments offer a native runtime pool. This currently requires
  a native llama.cpp-compatible installation advertising router support, shared
  device visibility and on-demand policy. Raw arguments are not supported in pools;
  use named configuration fields. Containers remain supervised deployments.
- A pool owns one router process. Models load independently on request. Enabling
  eviction permits native count-limited LRU and, when supported, device-memory
  margin unloading. Without eviction consent those limits are disabled. Stop
  stops the entire pool. Pinned/atomic residency requires supervised processes.
- Runtime residency and reported settings appear in deployment details. Native
  pool memory reports distinguish minimum predictions and effective allocations;
  these are not measured process peaks. Pool process telemetry is aggregate, not
  duplicated as per-model peaks.

## Configuration and capability intelligence

The deployment editor presents Model & runtime, Resources & context, Generation,
and Availability, with detailed controls progressively disclosed. Identity stays
compact; the standalone Advanced tab retains editable schemas and raw arguments.
Unspecified, explicit automatic, concrete override and observed values remain
distinct. Engine-specific values and omitted tuning round-trip without filling in
runtime defaults. Automatic context/slot sentinels no longer produce zero or
negative client-catalog capacity.

Capability discovery retains structured source/confidence evidence and unknown
states. Reasoning template controls are distinct from reasoning markers, effort,
budgets and output separation. Model findings and effective deployment findings
are shown separately; missing projector configuration is actionable, while a
configured projector is not assumed compatible. Manual variants and client
declarations remain available without claiming inference verification.

Executable-specific feature advertisements supplement the existing probe results.
Probe caches are invalidated when the executable changes. Published sampling
recommendations are optional, schema-checked and applied only by an explicit user
action. Native-pool engine/device controls are shared, and shared router options
are rejected in child presets without changing native scheduling or consent.

See the [configuration guide](../deployment-configuration.md).

## Limits

Capabilities advertised by help are not hardware acceptance. Older builds may
not implement every mechanism. llama.cpp fit assumes unlimited host memory, and
router estimates may omit projectors. Automatic settings can change between loads
as memory availability changes. Menagerie keeps measured host/GPU pressure and
temperature protection and never gates launches on predicted fit.

vLLM and other adapters retain supervised lifecycle; llama.cpp sleep/router
semantics are not assumed to apply to them. No new inference endpoints or engine
management endpoints are exposed through the public gateway.

Free-form model-card prose, arbitrary community reasoning mechanisms, specialized
kernel/model compatibility, and projector pairing are not universally inferred.
Unknown findings remain manual configuration paths, not launch prohibitions.

## Hardware acceptance status

The integrated configuration/intelligence changes are **not hardware-certified**.
Automated fixtures cannot satisfy the following release gates. Each requires an
authorized run with exact engine/model/build evidence and sanitized results:

| Scenario | Required acceptance | Status |
| --- | --- | --- |
| Upstream llama.cpp | Load, inference, context, concurrency, unload | Unverified |
| Prism-compatible executable | Specialized feature probe and supported inference | Unverified |
| Reasoning model | Correct control mechanism and output behavior | Unverified |
| Multimodal model | Compatible projector and image-input inference | Unverified |
| Native pool | Multiple models, routing, residency, eviction, resource attribution | Unverified |
| Unknown/unsupported feature | Warning, manual configuration, runtime error handling | Hardware unverified; synthetic coverage only |
| vLLM | Existing supervised configuration and inference regression | Hardware unverified; synthetic coverage only |

Representative GPU and CPU combinations must be reported individually. Unverified
combinations must not be described as passing or release-ready. Artifact packaging,
installed-wheel and target-platform acceptance remain separate release checks.
